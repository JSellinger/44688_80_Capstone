The sample projects all follow the broad format of most academic and what could be considered "high-level" papers. They contain the following general components: Title or Title Page, Abstract, Introduction, Body, Conclusion, and Bibliography. These parts make up any paper, whether scientific, literary, or purely recreational. The biggest difference is in the body, where you can include major sections and subsections with different narrative styles. In Socio-Analyzer: A Sentiment Analysis Using Social Media Data, the body structure follows a more scientific format with a Methodology and Results and Analysis section, each with its own subsections. This differs from Big Data Streaming Architecture for Edge Computing Using Kafka and Rockset, where the paper uses a "case study", although not in a classical business sense where we retroactively identify and analyze, but it follows an actual implementation of the proposed streaming architecture.

While I am unsure of the exact subsections I might employ, I am set on creating a paper that will double as a portfolio work for this class and for my professional understanding and development. My project will likely be a simple inventory risk and reorder point engine. This utilizes my specialized knowledge in supply chains and my current job experience while leveraging what I have learned in the coursework, although it may not demonstrate my proficiency in coding specifically, given that I will likely need AI to help do portions of it; it should reaffirm my understanding of my field and specialized knowledge, while also extracting useful data.

Given all the previous information, my report will likely follow this broad structure:

Title
This is the Title for the Paper - of course, with standard formatting
Abstract
This will give the rationale for the chosen project, an overview of the methodology, the results, the limitations, and the conclusion
Introduction
This is simply the rationale for the paper and the set-up for the ensuing research, case study, or intended purpose of the paper
Body, which will be composed of the following parts:  
Methodology Overview
This will give the broad architectural methodology that will be used so that one does not need to go through step by step but will be able to logically move into the step-by-step parts so that they could theoretically follow along
I will also document my software methodology within the paper itself, at least partially, so that should they require further reading they know exactly what files to look into in the Github. For example, I will likely use UV instead of pip to install the majority of packages and create a UV lock file so it captures everything. I was unfamiliar with UV at one point so it may prove useful to document some rationale for the use of certain choices in documentation as well but I will largely leave it in my Github documentation
Dataset
This will cover the dataset - it is important to note the data source, whether it is synthetic or natural, and the limitations of such a data source. It should also give an overview of the fields and columns of the dataset along with any other miscellaneous information that is pertinent to the project
Data Extraction
This will cover the exact method that was used to extract the data, whether I call it from a .py file and pull it directly in the way I need it, or I simply download it by hand and move it to the exact project file. It is simple, but vitally important should you want to recreate the project
Data Transformation
This will cover all transformations and the rationale behind the transformations - should I inject null values rather than dropping rows with null values, I should have a valid reason for the decisions and document it whether right or wrong
Data Loading
This will cover what I loaded my data into, whether I work directly from a .csv file or choose to load it to SQL or some other database. This choice should also be documented and there should be some rationale behind it.
ML model training
This will cover how I trained the machine learning model, the type of model, how it was trained, the rationale for the model chosen, and whether or not there are limitations to my choice and rationale
ML model evaluation
This will be the evaluation of my model to find specific limitations so that we can make inferences about when this model may fail, whether it be on edge cases or is even useful for deployment
Dashboard development
To cover an E2E pipeline, we would need a way to interact with the model through some form of GUI - that way, the end-user can interact or at least see the data in a helpful visual format. In essence, the degree is more about analysis and presentation of data rather than my ability to code, so I view this as a vital part. This may also have another subsection about how the dashboard will be deployed
Integration and Testing
This will be a rather small section, but because this will likely be done piecemeal and modular, there will need to be some time spent on integration and to give a good overview of how the parts actually connect
Deployment to the web
I believe a final, perhaps optional step, would be to deploy the project to the web - I would likely lack live-streamed data, but from an end-to-end view covering some form of hosting and deployment will be beneficial from a knowledge point of view and demonstration of skills.
Results and Analysis
This is the final part of the body paragraph where I will examine the results of my project and analyze how well it performs; we might simply perform an ad hoc evaluation or give it edge cases to see where it fails
Conclusion
This is the conclusion, broadly summarizing the work that was completed, the results, and analysis. This section should also at least have suggestions for more room for improvement, as that segue's directly into our limitations.
Limitations
While I will likely give limitations throughout the paper, having a limitations section at the end of the paper can summarize the found limitations and any other proposed larger limitations
Bibliography
This is the bibliography, a rather important part of any academic paper, as we stand on the shoulders of giants, so we must give credit where credit is due. Quite frankly, I stand on the shoulders of very tall giants in this regard.
